# Licensing policy

## Current source terms

The original owner control implementation identified in the [source licensing map](../LICENSING.md)
is available under GPL-3.0-or-later. Original Andrix material outside that explicit scope
remains Apache-2.0 unless otherwise noted. The full texts accompany the [license index](../LICENSE).
Individual file and component terms, inherited copyrights, notices and exceptions remain
applicable. Android, GrapheneOS, Linux, firmware, toolchains and browser components are not
relicensed by this choice. Nor does it establish permission to redistribute every external
build input or certify an eventual combined phone image.

## Owner control core

The original implementation central to Andrix's owner control uses
**GPL-3.0-or-later**. The objective is to preserve recipients' defined freedoms when covered
versions are conveyed, not merely to keep the project's own releases open.

The intended core includes original administration, identity, work management, supervision,
installation, update and recovery programs. Significant framework integrations belong in
that review too. Licensing scope follows the actual program and its combinations, not just
an Andrix directory, an intermediate build target or a separately packaged jar.

The "or later" choice permits recipients to select a future version of the GNU GPL. It
does not force them to leave GPLv3. This accepts the Free Software Foundation's stewardship
of future versions in exchange for greater long term licensing flexibility.

GPLv3's source and installation obligations apply under the license's actual conditions.
Its Installation Information provisions are qualified by the covered work, User Product
and conveyance facts. They are not a universal phone unlocking clause or a requirement to
publish every private signing key, independent firmware component or network service.
Andrix's practical build, owner signing, installation and recovery workflows remain an
engineering responsibility, not something completed by a license declaration.

## Permissive exceptions and inherited material

Apache-2.0 may remain appropriate for genuine public interfaces, minimal client definitions
and selected reusable integration or tooling where a concrete interoperability or reuse
reason justifies it. Such exceptions must be explicit and narrow. Calling authority or
validation implementation an "interface" does not by itself justify exempting it.

Existing upstream material retains its own licenses and grants. Compatible permissive
inputs may participate in a GPLv3 work with their applicable conditions and notices
preserved. GPLv2 only components and custom exceptions require their own analysis. Merely
shipping independent programs in one image or APEX does not automatically make them one
copyright program, and sharing a device does not make every application GPL.

Earlier valid Apache grants remain available. A future GPLv3 version cannot recall those
permissions or erase another copyright holder's rights. New original core contributions
released under this policy will not also be offered under an alternative Apache grant that
removes the intended reciprocal protection.

## Reuse, commerce and project identity

Use, modification, forks, redistribution and commercial activity are welcome when the
applicable license conditions are met. Copyleft is not a royalty system and does not
require every developer to contribute directly to Andrix.

The original core will not be offered under proprietary OEM exceptions that waive its
recipient protections. Funding, support and hardware partnerships must respect that
commitment. Pricing is a separate question from the rights granted to recipients.

Code reuse does not imply project endorsement or permission to present a derivative as an
official Andrix release. Any project branding policy is separate from the software license
and must not be used to obstruct legitimate code reuse.

## Maintaining the source scope

The source map, file headers and local build license modules identify the covered original
contributions and permissive exceptions. Maintain that explicit scope as code is added.
Retain inherited terms and review the actual program, dependency and notice relationships.
Architecture must remain coherent; artificial process boundaries are not a substitute for
licensing analysis.

A source policy decision is separate from binary distribution compliance. Eventual
releases need their actual artifact inventory, required notices, matching source provision
and applicable installation information. Existing source and artifact identities remain
historical evidence and must not be relabeled as newly built or newly qualified software.

GNU license, see the [GNU GPL version 3](https://www.gnu.org/licenses/gpl-3.0.html).
